# Documentation Audit

## Executive Summary

Aithy's README is a compact, mostly accurate setup guide for the current Bun/TanStack Start app. The highest-risk documentation problems are in the maintainer/agent-facing and user-facing operational copy: `AGENTS.md` still describes a removed `SOUL.md` file workflow, and the Settings UI describes global mounts with the wrong sandbox path. Those are not cosmetic; they point contributors and users at behavior the code no longer implements.

The repo has a broader documentation coverage gap around operational and safety surfaces. The codebase exposes system host-shell permissions, destructive reset flows, sandbox provider modes, Parallel Search settings, runtime services, and local SQLite state, but the shipped docs only cover these at README-bullet depth. That is acceptable for a first public README, but not enough for maintainers or users debugging a local agent runtime.

Validation was run locally. `bun install --frozen-lockfile` succeeded on retry, and `bun run check` passed supply-chain policy, line budget, typecheck, and 312 tests. A direct `bun test --version` probe was a bad probe because Bun treats it as a test invocation; on this machine's global Bun `1.3.11`, it failed one profile image test that requires Bun `1.3.14`. The repo pins `bun@1.3.14` in `package.json` and `bun run` puts `node_modules/.bin` first, so `bun run check` used the pinned local Bun after install.

## Findings

### Critical

None found.

### High

#### `AGENTS.md` documents a removed `SOUL.md` storage model

- Problem: `AGENTS.md` says `src/prompts/SOUL.md` is the packaged default, startup copies it to `~/.config/aithy/<bot id>/SOUL.md`, hashes it, processes it with AxGen, and stores processed data under the `soul.md` metadata key. The checkout has no `src/prompts/SOUL.md`; persona defaults come from `config/config.json`, and `SqliteSoulStore` persists fields under `bot.*` metadata keys.
- Evidence: `AGENTS.md:18`, `AGENTS.md:31-39`; `rg --files -g '*SOUL*' -g 'src/prompts/**'` returned no prompt files; `src/soul/service.ts:1-38`; `src/soul/sqlite-soul-store.ts:13-24`; `config/config.json:1-10`.
- Impact: A contributor or agent following `AGENTS.md` will add or debug the wrong file and database key, likely creating a parallel stale persona system instead of touching the shipped one.
- Fix: Replace the `SOUL.md` section with the current contract: default fields live in `config/config.json`, `loadOrSeedSoul` seeds on first run, mutable fields are stored in SQLite metadata keys `bot.name`, `bot.description`, `bot.coreNature`, `bot.communicationStyle`, `bot.behaviour`, `bot.negativeBehavior`, and `bot.updatedAt`, and the rendered responder description is generated by `renderResponderDescription`.
- Verification: verified - searched for `SOUL`/`src/prompts`, read `src/soul/service.ts`, `src/soul/sqlite-soul-store.ts`, `config/config.json`, and `AGENTS.md`.
- Confidence: High.

#### Global mount copy points users at the wrong sandbox path

- Problem: The Settings UI says global mounts are bind-mounted at `/workspace/mounts/<basename>-<hash>`, but the README and implementation use `/mounts/<name>`.
- Evidence: `app/components/settings-global-mounts.tsx:30-33`; `README.md:42-48`; `src/session/global-mounts.ts:27-40`; `src/agent/tools/mount-tools.ts` describes folder mounts under `/mounts/<name>`.
- Impact: Users trying to work with mounted folders from the agent sandbox will look in the wrong directory. That is especially painful because this feature is about making host files visible safely and predictably.
- Fix: Change the Settings subtitle to `/mounts/<name>` or `/mounts/<basename>-<hash>` using the same terminology as `computeMountName` and `prepareGlobalMountAdd`. Consider adding one README example that shows a host folder becoming `/mounts/<computed-name>`.
- Verification: verified - cross-checked user-facing copy, README copy, and the mount-path constructor.
- Confidence: High.

### Medium

#### `.env.example` omits several implemented and documented runtime knobs

- Problem: `.env.example` lists sandbox, state, and SQLite dylib variables, but omits Parallel Search variables documented in the README and other implemented environment controls such as `AITHY_SYSTEM_BASH_ENABLED`, `AITHY_WORKSPACE_ROOT`, `AITHY_SESSION_TTL_MS`, `AITHY_IDLE_PARK_MS`, and `AITHY_PARALLEL_AGENTS`.
- Evidence: `.env.example:1-13`; `README.md:28-30`; `src/config/env.ts:46-78`; `tests/config.test.ts:22-26`, `tests/config.test.ts:91-103`.
- Impact: New local users and operators have to discover important runtime settings by reading TypeScript tests/source. Search settings are especially awkward because the README explicitly names env vars that the example file does not show.
- Fix: Expand `.env.example` into grouped sections for state/workspace, sandbox, host shell, session/runtime limits, and Parallel Search. Mark optional values as commented examples and keep secrets commented.
- Verification: verified - compared `.env.example` against `loadConfig`, README setup text, and config tests.
- Confidence: High.

#### Operational docs do not cover destructive reset and host-shell permission surfaces

- Problem: The app exposes destructive state resets, memory resets, session deletion, and approved host-shell execution, but the docs do not provide a runbook or security model for those operations. `AGENTS.md` has short safety bullets; the README does not explain reset blast radius, `system.bash` approval behavior, or how to recover from state issues without data loss.
- Evidence: `AGENTS.md:42-49`; `scripts/fresh-start.ts:1-41`; `app/components/settings-danger-zone.tsx:87-105`; `app/server/system.actions.ts:8-15`; `app/server/memory.actions.ts:8-16`; `app/server/session.actions.ts:29-56`; `src/agent/tools/system-tools.ts:16-107`.
- Impact: Users and maintainers can delete local data or approve host commands without a durable explanation of scope, confirmation text, stored state, and recovery expectations. This is a local-first app, so local state safety is part of the product contract.
- Fix: Add `docs/operations.md` or a README section covering state locations, reset options, exact data removed by each path, host-shell approval flow, and safe troubleshooting commands. Link it from README and Settings danger-zone copy if this is meant for end users.
- Verification: verified - read the destructive scripts/actions, Settings danger copy, and system.bash approval implementation.
- Confidence: High.

#### Development command guidance is brittle around Bun version and local pinned Bun

- Problem: The README lists `bun test` as the full test suite command. The repo requires Bun `>=1.3.14` and also installs a local pinned `bun@1.3.14`; after install, `bun run check` uses `node_modules/.bin/bun`, but direct `bun test` uses the global Bun. On this machine, global Bun is `1.3.11` and direct test invocation failed because `Bun.Image` is unavailable.
- Evidence: `README.md:59-68`; `package.json:6-25`; `src/profile/images.ts:37-40`; `tests/profile-images.test.ts:18-24`; command output: `bun --version` was `1.3.11`, `node_modules/.bin/bun --version` was `1.3.14`, `bun run check` passed, and direct `bun test --version` invoked tests under global Bun `1.3.11` and failed `profile image processing > resizes accepted images to WebP avatars`.
- Impact: Contributors who skim the Development section after `bun install` can still run the wrong Bun binary and get a confusing failure. The README's version requirement is correct, but the command list does not steer users toward the repo-pinned runtime.
- Fix: Prefer `bun run test` in README, or add a short note: `bun install` installs the pinned local Bun; use `bun run check`/`bun run test` unless your global `bun --version` is at least `1.3.14`.
- Verification: verified - ran version checks, install, `bun run check`, and the direct test probe.
- Confidence: High.

### Low

#### `AGENTS.md` still mentions TUI-only slash commands without a visible TUI surface

- Problem: `AGENTS.md` says the TUI keeps `/file <path> [message]` and `/quit` local. The repo evidence found only the web app and shared slash-command handling; no TUI implementation or `/file`/`/quit` command handling was found.
- Evidence: `AGENTS.md:24-29`; `src/commands/slash-commands.ts` handles `/help`, `/skills`, and `/session`; `rg -n "TUI|/file|/quit" AGENTS.md README.md app src tests` only found the `AGENTS.md` TUI line.
- Impact: Low user-facing impact, but it is stale contributor guidance and may make agents preserve a non-existent interface.
- Fix: Remove the TUI sentence or replace it with the current web-only command split. If a TUI exists outside this repo, name that boundary explicitly.
- Verification: verified - searched command text and read the shared slash-command handler.
- Confidence: Medium.

#### No changelog, contributing, architecture, or troubleshooting docs ship with the repo

- Problem: The documentation surface is only `README.md`, `AGENTS.md`, and one bundled skill doc. There is no changelog, contributor guide, architecture guide, operations guide, or troubleshooting guide despite the app having multiple runtime services, SQLite stores, sandbox providers, queues, memory subsystems, and UI routes.
- Evidence: `rg --files -g '*.md' -g '*.mdx' -g 'README*' -g 'docs/**' -g 'CHANGELOG*' -g 'CONTRIBUTING*' -g 'SECURITY*'` returned `README.md`, `AGENTS.md`, and `config/skills/docling-processor.md`; public surfaces are visible in `app/routes/*.tsx`, `app/server/*.ts`, `src/runtime/**`, `src/memory/**`, and `src/sandbox/**`.
- Impact: This is survivable for early development, but it raises onboarding cost and leaves runtime behavior discoverable only through code.
- Fix: Add a short `docs/architecture.md` that maps app routes, server functions, runtime workers, SQLite stores, sandbox providers, and queues. Add `docs/troubleshooting.md` if this is expected to run on varied local machines.
- Verification: verified - inventoried docs, routes, server functions, runtime services, and code directories.
- Confidence: High.

## Recommended Plan

1. Fix stale correctness issues first: rewrite the `AGENTS.md` SOUL section and remove or qualify the TUI command sentence.
2. Correct the Settings global mounts subtitle to match `/mounts/<name>`, then add one README example for folder and file attachment paths.
3. Expand `.env.example` to mirror `loadConfig` and the README's Parallel Search env vars.
4. Add a short operations guide covering state directories, reset paths, memory/session deletion, `fresh-start`, host-shell approvals, and safe troubleshooting.
5. Add a small architecture map once the operations guide lands: routes, server functions, runtime services, queues, SQLite stores, sandbox providers, and memory pipeline.
6. Update README development commands to prefer `bun run test` or explicitly state the global Bun version expectation.
